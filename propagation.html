3Propagating the change

Rippling is the system of record. A change commits once it's approved and its effective date arrives. Each downstream system syncs as its own job. A third-party failure never blocks or rolls back the Rippling change, and never blocks payroll.

The order of events

1 · SubmitThe workflow's rules gate it: errors fixed or moved out; warnings acknowledged
2 · ApprovePer row, by threshold; sent-back rows become a follow-up draft
3 · Effective dateRules re-checked; then all rows together, or each as its approvals clear
4 · Rippling commitsThe record changes; this is the point of truth
5 · Products read itPayroll, benefits, time off, devices, workflows re-verify
6 · Apps syncOne job per app; retried, never rolled back

How we know which systems to update

Each integration subscribes to profile fields. The changed fields, crossed with those subscriptions and the people who have an account in each app, give exactly the systems on the Impact & approvals flowchart: what each one re-verifies, and which ones aren't affected at all. The IT owner sets the mapping up once; the HR admin never does.

The hard parts

Payroll cutoffFirst-partyLate approvals choose next run with retro pay, or off-cycle, before submit.
CurrenciesFirst-partyAmounts entered in one currency are paid in each person's own, at Finance's rate, cited on the cell.
Location changesFirst-partyTax state, leave policy and benefits region move with the work location. A new country is a transfer, not a bulk edit.
Partial approvalFirst-partyRows apply together, or each as it clears; sent-back rows never block the rest.
Dynamic segmentsFirst-partyMembership is frozen at submit, so approvers sign off on named people.
Rate limitsThird-partyBatch and throttle; show an ETA instead of an error.
App rejects a valueThird-partyRoute the app's own message to its owner. Rippling's value stands.
Irreversible effectsThird-partyAccess removals and email renames are framed as losses and wait for the effective date.
A rule changes mid-flightFirst-partyIn-flight drafts are re-evaluated and the owner sees the impact before activating. Flags already raised keep the version that raised them.
Something changes before the effective dateFirst-partyRules run again before commit. A manager who got a termination date after approval blocks only that row.
Very large changesBothAt 100,000 rows, writes, validation and impact run as server jobs with visible progress; the record is still committed only once.
ReversalBothA new draft pre-filled with the old values, through the same checks and approvals, linked in the audit log.
